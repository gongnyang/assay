# 루브릭 설계 — S2 축 유도 · aid 앵커 · 판정식

S2에서 `rubric.md`를 새로 쓰거나 G2·G3가 루브릭의 결함을 가리킬 때 로드한다. 이 문서는 점수 문구를 예쁘게 쓰는 법이 아니라, 근거가 있는 축만 통과시키는 계약이다.

## 1. 입력과 순서

루브릭은 `reach-gate.sh <run>`이 exit 0으로 수납을 허가한 뒤에만 작성한다. 가능한 aid 원천은 `<run>/anchors.jsonl` 하나다. `active:true`와 `verdict:CONFIRMED`가 아닌 앵커, 스냅샷 밖의 인용, 수집 메모는 축 근거가 될 수 없다.

1. `bench-init.sh <run-dir> <axes-csv> <min-req> <sum-req> <readonly>`로 축 ID, 합격선, readonly 범위, 승격 임계값을 `gate.conf`에 봉인한다.
2. CONFIRMED 앵커를 서로 나란히 놓고 레퍼런스가 실제로 다르게 하는 선택을 찾는다.
3. 축을 3~7개로 좁히고, 각 축의 0·3·4에 서로 검증 가능한 aid를 붙인다.
4. `rubric-lint.sh <run>`으로 형식과 참조 무결성을 통과시킨 뒤에만 S3로 간다.

축 이름은 결과물의 구현 기법이 아니라 판단 질문을 담아야 한다. "X 파일을 썼는가"보다 "독자가 X 결정을 확인 가능한가"가 축에 가깝다.

## 2. 축 후보 판별

레퍼런스가 모두 하는 것은 전제, 하나만 하는 것은 아직 약한 개성, 둘 이상으로 갈리고 각 쪽에 성공 사례가 있는 것은 축 후보다.

- **전제**: 전부 같거나, 위반하면 채점할 가치가 없는 조건이다. `gate.conf`의 통과/실패 전제로 내려 보낸다.
- **개성**: 한 사례의 취향·우연일 수 있다. 반대 방향의 실물이나 재현 가능한 결과가 없으면 축으로 올리지 않는다.
- **축**: 선택지가 있고, 그 선택의 0점·4점 양쪽을 실물 앵커로 댈 수 있다.

축마다 다음을 물어 확인한다.

```text
이 질문에 답하면 대상 사이에 실제 차이가 생기는가?
0점인 실물과 4점인 실물을 각각 다른 소스에서 지목할 수 있는가?
결과물이 아니라 레퍼런스의 선택 이유를 재고 있는가?
```

하나라도 아니면 축을 보류한다. 요약이나 인상으로 빈 앵커를 메우지 않는다.

## 3. 직교성과 전제

축 5±2개를 놓고 쌍마다 "A가 오르면 B도 거의 항상 오르는가"를 확인한다. 그렇다면 같은 것을 두 번 세므로 병합하거나 하나를 제거한다. 반대로 A를 높이면 B가 낮아질 수 있는 트레이드오프는 유익하다. S4의 파레토 규칙이 실제 선택을 하게 만든다.

전제를 축으로 올리면 모든 후보가 만점을 받아 변별력이 없어진다. 다음 신호는 전제 후보다.

- 수집한 모든 레퍼런스가 같은 점수를 받는다.
- 0점 실물과 4점 실물이 없거나 같은 소스 하나에서만 나온다.
- 점수 차이가 결과물의 품질이 아니라 존재 여부만 반영한다.

`rubric-lint.sh`는 전 레퍼런스 동일 점수 축을 exit 1 경고로, 두 축의 aid 집합이 완전히 같은 경우를 exit 2로 거부한다. 기계 검사는 근사치이므로, 경보가 나면 사람은 축의 질문과 양극 앵커를 다시 검토한다.

## 4. 0~4와 aid

`rubric.md`는 축마다 아래 형식을 쓴다. `aid`는 줄 안에 명시하고, 설명이 aid를 대신하게 하지 않는다.

```markdown
### A2. <축 이름>
질문: <한 문장>
자동검증: <measure 명령 또는 정성>

0 — <관찰 가능한 실패 서술>  aid: R-A#01
1 — <0과 2의 보간>
2 — <중간 상태>               aid: R-B#02
3 — <합격 최저선>              aid: R-C#03
4 — <레퍼런스 최고치>           aid: R-D#04
```

규칙은 엄격하다.

- 0·3·4에는 aid가 반드시 있어야 한다. 1·2는 보간일 수 있다.
- aid는 실제 `anchors.jsonl` 행을 가리킨다. 직접 인용문을 다시 복사하거나 파일명을 임의로 적지 않는다.
- 한 축의 0점과 4점 aid는 서로 다른 `sid`에서 와야 한다.
- 4점은 도달 불가능한 이상향이 아니라 확보된 레퍼런스 최고치다.
- 자기 결과물·현재 라운드의 앵커·감상문을 기준으로 삼지 않는다.

한글 파일명·한글 인용도 `excerpt`의 원문성에 영향을 주지 않는다. 문자열 대조는 ASCII 정규식이 아니라 유니코드 문자열 그대로 수행한다.

## 5. 자동검증과 승격값

자동으로 판정 가능한 조건은 0~4 점수 축이 아니라 전제다. 예를 들어 행 수·테스트 통과·라이선스 파일·번들 크기는 재현 명령과 TSV 셀로 증명되면 `gate.conf`의 R5 임계값이 된다. 임계 미달은 점수를 깎는 대신 채점 자체를 중단시킨다.

자동검증 축을 루브릭에 유지해야 할 때는 다음을 모두 쓴다.

```text
자동검증: <재현 가능한 measure: 명령>
출력: metrics/<무엇>.tsv
판정: <gate.conf에 봉인된 임계값과의 대조>
```

`rubric-lint.sh`는 `measure:` 필드와 `metrics/` 출력이 없는 자동검증 축을 거부한다. `measured:true` 앵커의 숫자는 같은 TSV 실제 셀과 일치해야 한다. 손으로 쓴 숫자는 근거가 아니다.

## 6. 판정식과 봉인

기본 판정식은 다음이며, 축 수와 척도에 맞춘 값은 S0에서만 정한다.

```text
PASS ⟺ min(axis) ≥ M AND sum(axis) ≥ S
```

- `M`은 한 축을 버리고 총점만 채우는 통과를 막는다. 0~4 척도는 보통 3에서 시작한다.
- `S`는 전 축이 최저선에만 걸린 결과를 막는다. 5축이면 17/20이 출발점이다.
- 가중치가 필요하면 역시 S0에서 고정한다. 라운드 중 `M`, `S`, 가중치, 축, 승격 임계값, readonly를 바꾸지 않는다.

합격선이 맞지 않는다는 진단은 합격선을 내리라는 신호가 아니다. 루브릭을 고쳤다면 새 런에서 R0부터 다시 시작한다.

## 7. lint와 자기 검증

`rubric-lint.sh <run>`은 다음을 기계로 막는다.

| 검사 | 실패 |
|---|---|
| 축 ID와 `gate.conf` CSV 완전 일치, 축 수 3~7 | 참조 무결성 exit 2 |
| 0·3·4 aid 존재, 활성 CONFIRMED 앵커 참조 | 참조 무결성 exit 2 |
| 0·4 aid의 서로 다른 sid | 설계 결함 exit 1 |
| 자동검증 `measure:`와 metrics 출력 | 설계 결함 exit 1 |
| 전원 동일 점수 축 | 전제 후보 경고 exit 1 |
| 두 축의 aid 집합 완전 일치 | 중복 축 exit 2 |

G3에서는 세 가지를 추가로 한다. 레퍼런스를 역방향으로 채점해 각 축에 3점 이상 사례가 있는지 본다. 전 축 만점인데 나쁜 반례를 만들고 그 반례가 통과하면 빠진 축을 찾는다. G2에서 두 점 이상 벌어진 축은 결과물을 고치지 말고 aid·서술을 보강한다.
