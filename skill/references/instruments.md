# 계측기 계약 — 대상별 TSV · 전제 게이트 · 신규 작성

G1의 대상별 계측기를 선택·작성·검토할 때 로드한다. 계측기는 정성 루브릭을 대신하지 않는다. 재현 가능한 전제를 exit code로 거부하고, 나머지 관측값을 TSV로 고정하는 도구다.

## 1. 공통 계약

계측기는 bash와 Python 3 표준 라이브러리만 사용한다. 결과는 `<run>/metrics/*.tsv`에 남기며, 한 행은 대상 하나다.

```text
target<TAB>metric_a<TAB>metric_b<TAB>...
```

- 첫 열은 사람이 읽을 수 있는 대상 이름 또는 경로다. 열 이름·순서는 실행마다 바뀌지 않는다.
- 실격 전제 미달은 exit 1이다. 계약·입력·출력 형식 오류는 exit 2, 실행 환경 결손은 exit 3, 인자 오류는 exit 64다.
- 값이 있다고 점수가 정해지지 않는다. 자동화 가능한 통과/실패 조건만 R5에서 `gate.conf` 임계값으로 승격한다.
- `measured:true` 앵커는 TSV의 실제 셀, 재현 명령, CONFIRMED 재검증을 모두 가진다. 숫자만 복사해 앵커를 만들지 않는다.
- 계측기는 대상의 파일을 바꾸지 않는다. 진단·측정은 읽기 전용이다.

## 2. 스킬 계측기

`measure-skill.sh <skill-dir> <run-dir>`은 스킬의 실행 표면과 로드 비용을 TSV로 기록하고 `gate.conf`의 승격 임계값과 비교한다. 하드코딩된 부모 이름이나 설치 경로를 전제로 하지 않는다.

권장 열은 다음과 같다.

| 열 | 의미 |
|---|---|
| `core_lines` | `SKILL.md` 행 수 |
| `core_fences` | 선언층 코드 fence 수 |
| `cmdish` | 실행 가능 명령처럼 보이는 표면 수 |
| `scripts` | `scripts/` 실행 자산 수 |
| `md_files`, `md_lines`, `md_fences` | 온디맨드 문서 수·행 수·fence 수 |
| `checks` | 검증 명령 또는 게이트 수 |

이 수치는 "문서가 짧을수록 좋다"는 점수가 아니다. 예를 들어 선언층 상한, references 파일당 상한, 필수 스크립트 존재처럼 재현 가능한 조건만 gate로 내린다. 미달이면 exit 1, 측정 완료와 임계 통과면 exit 0이다.

## 3. 레포 계측기

`measure-repo.sh <repo-dir> <run-dir>`는 M1~M7을 전제로 판정하고, M8~M18은 TSV 입력으로만 낸다. M1~M7 중 하나라도 위반되면 exit 1로 채점 자체를 중단한다.

| ID | 계측 | 구분 | 쓰임 |
|---|---|---|---|
| M1 | 루트 `README.md` 존재와 H1 정확히 하나 | 전제 | P1 |
| M2 | H1 뒤 300단어 안의 문장형 정의 | 전제·수동확인 | P2 |
| M3 | README의 설치·실행 명령 fenced block | 전제 | P3 |
| M4 | README 또는 루트의 라이선스 문자열 | 전제·수동확인 | P4 |
| M5 | 루트 `LICENSE*`와 API SPDX 인식 | 전제 | P5 |
| M6 | README·docs 링크 HTTP 200, 앵커 대상 헤딩 | 전제 | P6 |
| M7 | README 상대 이미지·파일 참조의 실제 존재 | 전제 | P6 |
| M8 | H1~첫 미디어 거리·미디어·배지 수 | 입력 | A1 |
| M9 | H1~첫 설치 block 거리·사이 헤딩 수 | 입력 | A1 |
| M10 | 첫 설치 block 앞 200자의 요구사항 표현 | 입력 | A2 |
| M11 | `docs/` 항목 수와 부속 Markdown 수 | 입력 | A3 |
| M12 | README에서 링크되지 않은 부속 Markdown 목록 | 입력 | A3 |
| M13 | releases/tags 수와 최근 태그 간격 | 입력 | A4 |
| M14 | workflow 수와 실제 테스트 명령 매치 | 입력 | A4 |
| M15 | 테스트 파일 수 | 입력 | A4 |
| M16 | CHANGELOG·RELEASE-NOTES 존재와 바이트 수 | 입력 | A4 |
| M17 | 한계·비목표·면책·기여정책 헤딩 | 입력 | A5 |
| M18 | README 헤딩의 레벨·순서·행번호 덤프 | 입력 | 전 축 |

M8·M14·M17은 존재 여부를 점수로 바꾸지 않는다. 예를 들어 배지 수나 workflow 수 자체는 품질이 아니다. 독립 채점자는 TSV를 보고 실제 실행 증거·테스트 실행·경계 선언의 질을 앵커와 함께 판단한다.

외부 링크·API를 점검하는 M5·M6은 네트워크 환경이 없으면 통과를 가장하지 않는다. 도구·네트워크 부재는 exit 3으로 명시하고 `reach-doctor.sh`의 환경 진단으로 넘긴다.

## 4. 새 계측기 작성

새 대상 유형에는 다음 순서로 계측기를 만든다.

1. 루브릭에서 자동으로 증명 가능한 조건과 정성 판단을 분리한다. 정성 판단을 숫자로 위장하지 않는다.
2. 자동 조건마다 입력·출력·실패 기준·재현 명령을 적고, 가능한 경우 R5 앵커로 만든다.
3. 첫 줄 헤더와 고정 열 순서를 정해 `metrics/<이름>.tsv`에 쓴다.
4. 모든 전제 통과면 0, 전제 미달이면 1, 계약 오류면 2, 환경 결손이면 3, 사용법 오류면 64를 낸다.
5. `rubric.md`의 `measure:`와 outputs를 연결하고 `rubric-lint.sh`로 실재를 확인한다.

최소 인터페이스 예시는 아래다.

```bash
measure-example.sh <target> <run>
# stdout 또는 <run>/metrics/example.tsv:
target<TAB>required_ok<TAB>observed_value
```

명령은 결정론적이고 읽기 전용이어야 한다. 시간·네트워크·도구 버전처럼 흔들릴 수 있는 값은 `observed_at`, 도구 버전, 실패 이유를 함께 남긴다. 같은 입력에서 달라지는 판단은 정성 축으로 되돌린다.

## 5. 증거 연결과 금지사항

계측값은 다음 흐름으로만 게이트가 된다.

```text
measure 명령 → metrics/*.tsv 실제 셀 → anchors.jsonl(measured:true)
→ CONFIRMED 재검증 → bench-init.sh의 gate.conf 봉인 → G1 재실행
```

아래는 금지한다.

- TSV가 없는 `measured:true` 앵커
- 숫자를 임의로 0~4 점수로 변환해 축의 실물을 대체하는 것
- 미달을 note에 적고 exit 0으로 통과시키는 것
- 측정 뒤 임계값·열 정의·대상 경로를 바꾸는 것
- 테스트처럼 보이지만 아무것도 검사하지 않는 스텁 계측기

G1은 gate 임계 미달을 통과로 기록하지 않는다. PASS 전에는 계측기 exit 0, 실제 TSV, 앵커, 독립 채점이 같은 축을 서로 비어 있지 않게 지지해야 한다.
